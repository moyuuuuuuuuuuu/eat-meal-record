# 扣子工作流耗时优化记录

日期：2026-09-21。状态：四个优化草稿已保存并完成下述测试；尚未发布任何工作流变更，线上API未切换。

## 优化对象

用户确认：一分多钟是在扣子后台单次运行中观察到的，不只是小程序等待时间。因此本轮优先优化工作流内的模型执行，不能用缩短轮询、增加服务端并发或缓存命中来冒充单次未缓存执行提速。

服务端 `app/service/FoodService.php` 接入四种工作流：餐食识别、标签、单位、食品完整营养。它们有不同调用入口，不是每次识别都会依次调用四个工作流。当前餐食识别任务调用一次识别工作流后进行食品同步落库。

## 已核对的食品营养工作流

- [food_nutrition 编辑页](https://www.coze.cn/work_flow?workflow_id=7678227370758701056&space_id=7501669478888325132)
- 可见节点：开始 → 大模型 → JSON校验 → 结束。
- 大模型：豆包·2.0·pro；Chat API；深度思考开启，程度中。
- 最大回复长度4096；最大推理与回答长度0（界面原值，不能据此理解为不推理）。
- 未配置模型技能；续写关闭；节点整体超时180秒；不重试。
- 系统提示词要求最多35个名称，每个食品含11项营养、单位、标签和分类；返回接口仍是output字符串。

## 本轮对比原则

先固定输入、模型、提示词、输出契约，仅调整深度思考。记录整个工作流和模型节点耗时、Token用量、返回名称数量、校验结果。只有结构完整且没有明显单位/数量退化的候选才保留；这不等同于营养数值经过权威数据校准。

第一组固定输入为 `["八宝粥","水煮鸡蛋","苹果"]`。再用不同输入及较大批量检查是否截断，不以单次最快值声称长期提速比例。若关闭思考仍不足，再在同一评测集比较Lite等模型，不能同时改模型和多个参数后归因。

## 必须保留的业务约束

- 食品名称与输入对应，不漏项后假报完整成功；无法识别应按现有明确失败/过滤规则处理。
- 完整营养工作流的11个营养字段目前被服务端校验器要求，不能直接删成仅4个宏量字段。
- 单位必须有正克重、明确类型和唯一默认项；固定单位换算不应冒充某次实际摄入。
- 单位、标签也是当前同步契约的一部分，不能为了速度直接去掉。
- JSON校验节点保留；禁止把未知营养补0作为性能优化。
- `template/text` 等文件属于旧的Nutrition服务模板，并非已核实的当前扣子提示词来源；不修改它们来声称线上工作流已优化。

## food_nutrition 的有效性与耗时实验

原配置3种食品54秒（模型53秒，校验0.064秒），3811 Tokens，3/3返回完整。主要耗时在模型，不在Python校验。

以下候选不能仅根据最快耗时采纳：

| 候选 | 结果 | 处理 |
|---|---|---|
| 原输出String，仅关闭思考 | 3条14秒、1376 Tokens，但照抄示例的叶酸值与mg口径冲突 | 不能单凭结构通过认定正确 |
| 删除数值示例 | 10条50秒通过；3条14秒却有多余括号 | 撤回该提示词实验 |
| 恢复结构示例并说明单位 | 3条12秒通过；10条38秒出现非法JSON | 排除，不能把空数组当成功提速 |
| Text输出String | 10条模型42秒，非法JSON | 撤回 |
| 原生数组，营养仍为name/value长数组 | 模型1.01分钟，10条结构有效；首次端到端因编辑时校验代码截断失败，修正后用同一真实输出单独测试校验节点返回10条 | 不是端到端成功基准；继续压缩内部输出 |

最终草稿采用原生数组及紧凑营养对象：模型内部将营养写成11个数值字段，校验出口恢复`[{name,value}]`，tags也转回现有中文类型字典，最终output仍为JSON字符串。外部接口不变。3条一次、10条连续两次端到端试运行均通过；尚未验证提示词中原有35条上限，服务端现有批处理按10条运行，不将本次结果外推为35条已稳定支持。

配套资产：系统提示词[food-nutrition-prompt.txt](food-nutrition-prompt.txt)，用户提示词保持`{{input}}`；[food-nutrition-schema-example.json](food-nutrition-schema-example.json)仅供扣子“JSON导入”生成字段类型，不是营养参考数据。生成后确认output为Array<Object>、tags为Array<Object>（type/values）、nutrition为Object且11字段均为Number、units.weight为Number。模型仍为Pro、最大回复4096、不重试、续写关闭；深度思考关闭。

校验器原先对非法JSON捕获后返回`[]`，会把模型格式错误伪装为成功。本轮改为抛出`INVALID_WORKFLOW_JSON`；错误根类型抛出`INVALID_WORKFLOW_ARRAY`。合法空结果仍保留原契约，业务字段不完整的条目仍按原规则过滤，不通过补0凑齐数据。节点导出在[food-nutrition-validator.py](food-nutrition-validator.py)。

离线验证：`python3 tests/coze_validator_test.py`，8项通过，覆盖非法/截断JSON、错误根类型、合法空数组、旧字符串兼容、原生数组、紧凑营养对象与缺失营养项、标签转换、重复名称、默认单位和小数值。扣子负向节点测试确认非法JSON会报错。

## 发布与回滚边界

- 全部工作流变更留在草稿；未点击发布、未改线上凭据或数据库。后续用户已授权将本地代码和本文档提交推送以便换设备，详见[交接更新](../handoff/2026-09-21-device-switch.md)，Git推送不代表扣子发布。
- 单位、标签、文字识别的回退方式是相应模型节点重新开启深度思考，程度中；其他配置未改。
- food_nutrition 的输出结构、提示词、Python校验器必须配套；回退时整体恢复改动前版本，不能只把Array改回String而保留不匹配的提示词。
- 发布后还需要通过真实后端接口和小程序做一次联调；本轮扣子试运行不等同于线上端到端验收。
- 本轮验证的是结构、完整性与耗时，并非权威营养数据校准。发现原校验器统一保留2位小数会把很小的mg值舍入为0；数值精度、可信来源和“未知”语义应在食品数据质量任务中一并处理，未在本轮扩大修改。

## 后续代码侧事项

当前统一SDK调用只返回data，未保留debug_url和阶段耗时。后续可增加调用耗时、鉴权耗时、同步耗时和可追溯的运行标识；日志避免保存饮食原文、媒体和凭据。批处理缓存可以减少重复执行，但不计入工作流本身的提速数字。

服务端同步HTTP超时480秒不等于扣子平台可执行480秒。扣子非流式运行接口文档说明90秒未响应会断开；流式/异步用于改善传输与长任务可靠性，不能让同一模型计算自动变快。是否改异步需核对账号能力和任务恢复机制，不在本轮盲目切换。
